## Deep Dive Findings

### 1. E2E Scenario 17 Flakiness (`17_enemy_death_drops_loot.py`)
- **Location**: `tests_e2e/scenarios/17_enemy_death_drops_loot.py`
- **Logic / Spec Gap**: 
  The scenario spawns a single Common enemy and kills it using the `kill_enemy_by_id` cheat, then immediately asserts that a new `FloorItem` appeared on the ground.
  However, in `configs/loot.yaml`, the loot pipeline was updated to be chance-gated:
  ```yaml
  BASE_DROP_CHANCE: 0.25
  ```
  In C++, `EnemyManager::spawnDeathLoot` calls `LootMaker::rollAllDrops`, which rolls against the computed drop chance:
  ```cpp
  const float dropChance = computeDropChance(luckTotal, enemyTierIndex);
  if (rngRef.uniformFloat(0.0f, 1.0f) < dropChance) { ... }
  ```
  At neutral settings (Common enemy, 0 luck), `dropChance` is exactly 0.25 (25%). Therefore, 75% of the time, killing the enemy drops **no loot**, causing the test assertion to fail:
  `FAIL 17_enemy_death_drops_loot.py: no new FloorItem appeared after killing the enemy; before=[5]; after=[5]`
- **Proposed Remedy (when writing code is permitted)**:
  Update `17_enemy_death_drops_loot.py` to spawn an **Elite** enemy (which has a guaranteed extra drop of `ELITE_DROP_COUNT_BONUS = 1`) or inject player luck to force the drop chance to saturate, making the test fully deterministic.

### 2. E2E Python Runner Socket Timeout Cascade
- **Location**: `tests_e2e/run_e2e.py:L40`
- **Issue**:
  The E2E client sets a 2.0-second socket timeout:
  ```python
  self.socket.settimeout(2.0)
  ```
  If any single command round-trip (or scenario) takes more than 2.0 seconds, the Python client raises a socket timeout, aborts the run, and terminates the `dogmax` process. Because `run_e2e.py` runs all scenarios sequentially on the same process connection, a timeout in one scenario causes all subsequent scenarios to fail with `BrokenPipeError`.
- **Contributing Bottlenecks**:
  - `configs/automation.yaml` defines `AUTOMATION_READ_TIMEOUT_MS: 50`.
  - In `AutomationServer::serviceSocket`, if `socket.receive` returns `sf::Socket::Status::NotReady`, it sleeps for `readTimeoutMs` (50ms).
  - Because Python runs synchronously (send command → block waiting for response), the C++ thread often goes to sleep for 50ms before checking the socket again, introducing a huge artificial delay (up to 50ms per round-trip).
  - In `20_weapon_slot_count.py`, there are 2000 sequential round-trips. With GDB overhead or CPU scheduling latencies in CI, this scenario easily hits the 2.0s limit.
- **Proposed Remedy (when writing code is permitted)**:
  - Increase python socket timeout in `run_e2e.py` to `10.0` or `15.0` seconds to accommodate large tests and GDB overhead.
  - Decrease `AUTOMATION_READ_TIMEOUT_MS` to `2` or `5` ms in `configs/automation.yaml` to prevent long waits when polling.

### 3. E2E FloorItem Accumulation (Memory Leak)
- **Location**: `tests_e2e/scenarios/20_weapon_slot_count.py`
- **Issue**:
  The test calls `spawn_loot_drop` 2000 times, which internally spawns 2000 `FloorItem` instances.
  `World::removePickedUpFloorItems()` is only called when items are picked up (via `PickupHub.cpp`).
  Since the test never picks them up, all 2000 items remain in `world.floorItems()` for the duration of the scenario. `FloorItemManager::update` has to loop over 2000 items every simulation step, causing performance degradation.
- **Proposed Remedy (when writing code is permitted)**:
  Clean up floor items inside scenario 20, or add a cheat method to clear transient floor items.
